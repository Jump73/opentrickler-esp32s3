# Flow Model + PD Autotune Integration Recommendations (No-Precharge Architecture)

## Assumptions

1. No precharge/priming/spin-up stabilization is available and must not be introduced.
2. Two motors exist with different dynamics: coarse (high flow, larger in-flight mass) and fine (low flow, higher precision).
3. Scale has latency + low-pass filtering; observed weight is delayed relative to powder release.
4. Powder transport delay and inertia are non-negligible and drift across sessions.
5. ESP32 runtime budget requires deterministic, light-weight adaptation (EMA/RLS-level complexity only).

---

## A) Design conflicts between flow-model learning and PD autotune

### Conflict 1: Closed-loop identification bias
Autotune trials change Kp/Kd and therefore alter the excitation pattern (speed trajectory, dwell time per bin).
If autolearning updates model parameters at the same time, identified flow map is conditioned by unstable/transient controllers, not by the nominal controller used in production.

Result:
- Biased `speed->flow` estimates.
- Over-representation of aggressive regions (near saturation/max speed).
- Non-stationary data distribution during optimization.

### Conflict 2: Moving-plant during optimization
Classical autotune assumes plant is fixed while evaluating candidate gains. If flow model is adapting simultaneously, effective plant estimate is changing between candidate evaluations.

Result:
- Candidate score variance increases.
- Evolutionary/iterative tuner may chase a moving objective.
- Convergence slows or collapses to overly conservative gains.

### Conflict 3: Coupled adaptive loops (parameter chasing)
Loop A (autotune): adjusts controller gains to reduce tracking error.
Loop B (autolearn): adjusts plant model using data generated by Loop A.
Without timescale separation and gating, both loops react to each other.

Result:
- Oscillatory meta-dynamics (gain chasing model chasing gain).
- Poor repeatability between autotune runs.

### Conflict 4: Delay-estimation contamination
Autotune intentionally explores dynamic behavior (including aggressive starts/stops), which can distort transport-delay and inertia estimates if those samples are ingested with equal weight.

Result:
- Delay/in-flight estimates drift upward from trial artifacts.
- Predictive stop thresholds become conservative or inconsistent.

---

## B) Recommendation: disable direct autolearn parameter updates during autotune, but keep shadow data logging

## Decision
Use a **frozen active model** during autotune. Do **not** let autotune mutate the live flow model used for control decisions.

However, keep recording autotune data to a **shadow buffer/model** for diagnostics. Merge into live model only if explicit acceptance criteria are met after autotune finishes.

## Why this is best (control-theory rationale)
1. **System-identification validity**: controller comparison requires approximately invariant plant; freezing model preserves comparable trial conditions.
2. **Adaptive stability**: separates adaptation timescales (fast: PD tuning; slow: model learning), avoiding coupled-loop instability.
3. **Reduced excitation bias**: autotune data is atypical (high excitation), so it should be downweighted or quarantined.
4. **Deterministic convergence**: objective landscape for autotune remains stable.

## Practical policy
- During autotune:
  - `model_live`: read-only for prediction.
  - `model_shadow`: updated from autotune samples with very low alpha (or full-batch fit).
- After autotune:
  - If new gains accepted and shadow quality metrics pass (coverage, residual error, outlier rate), perform bounded merge:
    `model_live <- (1-beta)*model_live + beta*model_shadow`, with `beta <= 0.15`.
  - Else discard shadow.

## C) Final control architecture (PD + predictive + learning)

## 1) Hierarchical structure
1. **Trajectory layer (predictive setpointing)**
   - Computes stop thresholds and phase-switch mass using delay/in-flight estimates.
2. **Inner motor-speed loop (PD)**
   - Tracks desired speed command for active phase.
3. **Learning layer (slow adaptation)**
   - Updates flow map, delay, in-flight mass, and switch margin only from validated dispenses.

## 2) Recommended command law per phase
Let `e_m = target_mass - measured_mass`.
Let `m_pred = measured_mass + m_inflight_est`.
Use PD to compute desired flow-rate proxy:

`u = Kp_phase * (target_mass - m_pred) + Kd_phase * d/dt(target_mass - m_pred)`

Convert to motor speed via inverse map:

`speed_cmd = clamp( inv_flow_map_phase(u), speed_min_phase, speed_max_phase )`

Key point: predictive mass (`m_pred`) is used inside PD error to account for delay/inertia.

## 3) Phase management
- Coarse active until predicted handoff condition is met:
  `m_pred >= target_mass - switch_margin`
- Fine active until final predictive stop:
  `m_pred >= target_mass - final_margin`

Where margins are learned, bounded:
- `switch_margin` target range: 0.5-0.8 gn.
- `final_margin` near zero but positive to prevent overshoot under delay.

## 4) Gain scheduling
Use distinct gains per phase:
- Coarse: lower Kp, stronger Kd damping for larger delay/inertia.
- Fine: higher Kp, moderate Kd for precision.

## D) Pseudocode state machine (coarse/fine)

```pseudo
STATE IDLE:
  wait start command
  load profile + model_live
  reset estimators
  goto COARSE_INIT

STATE COARSE_INIT:
  phase = COARSE
  enable coarse motor
  t_phase_start = now
  goto COARSE_RUN

STATE COARSE_RUN:
  w = filtered_scale_weight()
  w_dot = derivative_estimator(w)
  m_inflight = estimate_inflight(COARSE, speed_coarse, model_live)
  m_pred = w + m_inflight

  e = target - m_pred
  de = derivative(e)
  u = Kp_coarse * e + Kd_coarse * de
  speed_cmd = inv_flow_map(COARSE, u)
  speed_cmd = rate_limit(speed_cmd)
  set_coarse_speed(speed_cmd)

  if m_pred >= target - switch_margin:
      stop coarse
      log coarse settle samples (post-stop window)
      goto FINE_INIT

  if timeout or fault: goto ABORT

STATE FINE_INIT:
  phase = FINE
  enable fine motor
  goto FINE_RUN

STATE FINE_RUN:
  w = filtered_scale_weight()
  w_dot = derivative_estimator(w)
  m_inflight = estimate_inflight(FINE, speed_fine, model_live)
  m_pred = w + m_inflight

  e = target - m_pred
  de = derivative(e)
  u = Kp_fine * e + Kd_fine * de
  speed_cmd = inv_flow_map(FINE, u)
  speed_cmd = rate_limit(speed_cmd)
  set_fine_speed(speed_cmd)

  if m_pred >= target - final_margin:
      stop fine
      log post-stop settle samples
      goto SETTLE_VERIFY

  if timeout or fault: goto ABORT

STATE SETTLE_VERIFY:
  wait settle_window_ms
  w_final = filtered_scale_weight()
  err_final = target - w_final

  if err_final > refill_deadband:
      // small underweight correction burst
      goto FINE_INIT
  else:
      goto LEARN_UPDATE

STATE LEARN_UPDATE:
  if mode == NORMAL_DISPENSE:
      update_model_live_with_gated_rules()
  else if mode == AUTOTUNE:
      update_model_shadow_only()
  save logs/metrics
  goto DONE

STATE ABORT:
  stop all motors
  mark cycle invalid for learning
  goto DONE
```

## E) Improved autotune for delayed inertial granular flow

## Objective
Tune `(Kp, Kd)` per phase minimizing overshoot and settle time under delay.

## Proposed procedure
1. **Freeze live flow model** for whole autotune session.
2. **Two-stage tuning**:
   - Stage 1: coarse-only micro-target tests (e.g., 8-12 gn equivalent window around mid-bin speeds).
   - Stage 2: fine-only completion tests (small error band near target).
3. **Cost function (per trial)**:

`J = w1*max(0, overshoot_gn) + w2*settle_time_s + w3*IAE + w4*control_variation`

Where:
- `overshoot_gn` strongly penalized (set `w1` highest).
- `IAE = integral |e(t)| dt` on prediction error.
- `control_variation = integral |du/dt| dt` discourages aggressive jitter.

4. **Safety constraints**:
- Reject candidate if overshoot > hard_limit (e.g., 0.10 gn fine test or profile-specific).
- Reject if oscillation count > N.

5. **Search strategy**:
- Use bounded coordinate search or small evolutionary population, but evaluate each candidate on multiple repeats (>=3) to average scale noise.
- Enforce monotone damping heuristic:
  - If overshoot events increase, reduce Kp or increase Kd region.

6. **Acceptance**:
- Candidate accepted only if median overshoot and 90th percentile settle time both improve baseline.

## Optional relay identification (lightweight)
Before search, run one conservative excitation step per phase to estimate apparent dead-time `L` and time constant `T`, then initialize gains near PD dead-time-compensating heuristics:

`Kp0 ~ a * (T / (K*(L+eps)))`, `Kd0 ~ b * L`

(Use this only for initialization; final gains still empirical.)

## F) Stable autolearning update rules (won't fight controller)

## 1) Update gating
Apply learning update only when all are true:
- Dispense completed without fault/cancel.
- No actuator saturation longer than `sat_max_frac`.
- Scale quality good (noise RMS < threshold).
- For bin update: enough dwell samples in steady region.

## 2) Timescale separation
- Normal dispense: moderate EMA (`alpha_flow` ~ 0.05-0.20 depending on quality).
- Immediately after autotune: temporary reduced alpha (e.g., 0.5x for next N dispenses).

## 3) Residual-based robust update
For each bin, compute residual `r = flow_obs - flow_pred`.
Use Huber-like influence:

`g(r) = r                  if |r| <= delta`
`g(r) = delta*sign(r)      otherwise`

Update:

`flow_bin <- flow_bin + alpha * g(r)`

Prevents single anomalous throws from shifting model excessively.

## 4) Delay and in-flight adaptation bounds
Update with clipped increments:

`delay <- clamp(delay + alpha_d * clip(r_delay, -dmax, dmax), d_min, d_max)`

`inflight <- clamp(inflight + alpha_i * clip(r_i, -imax, imax), i_min, i_max)`

Use smaller alpha for delay/inflight than for flow bins.

## 5) Phase-switch learning rule
Let coarse handoff error after settle be `e_h = (target - w_after_fine_start_reference)`.
Adjust switch margin slowly:

`switch_margin <- clamp(switch_margin + alpha_s * e_h, 0.5, 0.8)`

Use deadband around zero to avoid dithering.

## 6) Confidence-weighted usage
Only allow predictive aggressive behavior when model confidence is high (sufficient bins + low residual variance). Otherwise fallback to conservative PD limits and fixed margins.

## G) Validation metrics and test procedure

## Metrics (log per dispense)
1. **Final error**: `e_final = target - w_final` (mean, std, P95 abs).
2. **Overshoot rate**: % dispenses with `w_peak > target`.
3. **Phase timing**: coarse duration, fine duration, total cycle time.
4. **Handoff quality**: mass at coarse stop and at fine start settle.
5. **Prediction quality**:
   - RMSE of `m_pred` vs settled mass trajectory.
   - Delay estimate drift over time.
6. **Control effort**:
   - Speed command variance.
   - Saturation fraction.
7. **Learning stability**:
   - Per-bin update magnitude statistics.
   - Residual variance trend (should decrease then plateau).

## Acceptance targets
- Coarse handoff: typically target-0.5 to target-0.8 gn.
- Zero-overshoot or near-zero overshoot policy for fine completion.
- Total dispense time median in 15-20 s band.
- Repeatability: standard deviation of final error below profile-specific threshold (define per scale resolution).

## Test procedure
1. **Baseline**: run 30 dispenses with learning OFF, fixed gains.
2. **Learning ON (normal mode)**: run 50-100 dispenses, verify monotonic improvement in prediction RMSE and final-error variance.
3. **Autotune isolation test**:
   - Run autotune with frozen live model + shadow logging.
   - Confirm live model hash unchanged during autotune.
4. **Post-autotune validation**:
   - Run 30 dispenses normal mode with new gains.
   - Compare against baseline on overshoot, repeatability, and time.
5. **Disturbance robustness**:
   - Repeat with powder lots/ambient changes; verify adaptation recovers without overshoot spike.

## Instrumentation recommendation
Persist per-dispense summary in compact ring buffer (NVS or RAM+periodic flush):
`{timestamp, profile, phase_times, overshoot, e_final, model_confidence, delay, inflight, gains, autotune_flag}`.

This enables objective pass/fail and future offline tuning without heavy on-device computation.
